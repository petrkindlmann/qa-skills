# Curation of the generated Playwright corpus

Skill: `test-suite-curation` 1.1. Corpus: `tests/workflows/generated/` (baseline-shop, baseline-todo, review-followup, addons, campaign3/*), 90 tests in 22 spec files across 11 suites, against the Shop (contract `tests/workflows/fixture-app-contract.md`) and the pinned TodoMVC (contract `tests/workflows/todomvc-contract.md`). Candidate commit 958fcc0, Node 26.0.0, Playwright 1.62.1, Chromium, 2 workers, retries 0, 2026-10-21.

Everything below was produced by the scripts in `tools/` from the collected inventory, the traces of one instrumented run and the spec sources; the per-test judgements in the decisions table are mine, read from the code. Raw outputs are in `analysis/`.

## 0. Result in one paragraph

The corpus is 20 % redundant by test count and the redundancy is concentrated in two places: `campaign3/selector-drift-recovery/todomvc.spec.mjs` is a byte-identical copy of `baseline-todo/todomvc.spec.mjs` (only the two import depths differ), and six of the seven migrated Cypress tests in `campaign3/test-migration/` assert strict subsets of baseline-todo or review-followup tests. Three Shop tests are subsets of other Shop tests (one review-followup logout test, two bug-reproduction idempotency tests). That is 18 tests. The seventh migrated test is the opposite case and the reason the skill's load-bearing rule matters here: it has the same coverage as the baseline create test but a stricter oracle (raw `textContent`, where the baseline's `toHaveText` normalises whitespace and cannot see a missing trim), so it stays. Everything else is unique by behaviour or by oracle. The curated suite keeps 72 tests in 21 files, guards every one of the 58 contract clauses and extra behaviours the original guards (0 lost), and passed twice in a row: 71 executed, 0 failed, 0 flaky, 10 skipped (9 quarantined in place with `test.skip`, 1 opt-in detector check). No test was deleted: the 18 quarantined tests are either not copied into `curated/` (the byte-identical file) or copied as `test.skip` with their audit row, and their original folders are untouched. No mutation check could be run against these black-box applications, so under the skill's own rule (SKILL.md §2, §8) none of the 18 may be removed yet; they wait for a named approver and an observation window.

## 3. Duplicates and near-duplicates

### 3.1 What the clustering found

Three normalisations were run (`tools/analyze.mjs`), all average-linkage, cut at 0.85 and 0.70:

| signal | clusters at 0.85 | tests in them | what the clusters are |
|---|---|---|---|
| skill-faithful AST (all identifiers -> VAR, literals -> CONST) | 9 | 34 | 2 clusters of 7 and 9 Todo tests that mix the real baseline/drift pairs with behaviourally different neighbours (create vs complete vs delete), the 5 monitoring probes, the 3 parametrised visual tests, the migration pair 25/37, the virtualized-ui pair 429/500, and 3 clean baseline/drift pairs |
| AST with member names kept (`toHaveText`, `check`, `getByRole` survive) + static profile, 0.6/0.4 | 9 | 22 | 8 clusters are exactly the baseline/drift pairs (one of them a 5-member cluster that also pulls in review-followup `single delete persists immediately`), plus the probes and the visual loop |
| skill-faithful AST + dynamic request profile, 0.6/0.4 | 9 | 34 | one 16-member Todo cluster: every Todo test makes exactly one request (`GET / 200`), so the dynamic profile is 1.0 between all of them and cannot separate anything |
| dynamic request profile alone, 0.90 | 6 | 52 | the 29 Todo tests collapse into one cluster; Shop tests cluster by endpoint family |

What this says about the recipe: the normalisation in clustering.md erases exactly the tokens that carry a Playwright test's meaning (which matcher, which action), so structurally similar tests of different behaviours score 0.87-0.98. Keeping member names fixes most of it. The five probe specs are three-line wrappers around functions in `probes.mjs`, so their spec bodies are near-identical by any syntactic measure (1.0 for health vs storefront); the "require both signals" rule (clustering.md:55) does not rescue them because their dynamic profiles overlap too. Reading the probe bodies is the only way to tell them apart. The three visual filter tests share one body in a `for` loop; a 1.0 score there is the loop, not a copy.

The true duplicates in this corpus are whole-file copies, and `diff` finds them in one command (`diff baseline-todo/todomvc.spec.mjs campaign3/selector-drift-recovery/todomvc.spec.mjs` shows lines 1-2 only). The clustering confirmed it and otherwise produced candidates that had to be read.

### 3.4 Same coverage, different oracle (kept on the skill's load-bearing rule)

- `test-migration:16` vs `baseline-todo:6`: same request set, same UI path. The migrated test asserts titles with `allTextContents()` + `toEqual`, the baseline with `toHaveText`, which normalises whitespace. Only the migrated test fails if trimming stops. Kept, and credited with clause T1t.
- `review-followup/shop-review:33` (unit prices, quantity 10): its request set is a subset of `purchase-events:13`, `stub-fidelity:11` and the order-journey probe, yet no other test asserts 1200 and 1800 as separate orders or accepts quantity 10. Kept.
- `review-followup/shop-review:63` (non-canonical JSON signed byte-for-byte): request set subset of `baseline-shop:42`; unique oracle. Kept.
- `bug-reproduction/report-1:9` (UI Sign out revokes a copied cookie): `baseline-shop:71` also signs out through the page and sees a 401, but through the same cookie jar after the server cleared the cookie, which does not prove server-side revocation. Kept.
- The synthetic probes `sign-in` and `order-journey` are the weakest keeps: every behaviour they assert is asserted elsewhere; their unique oracles are author-chosen latency budgets. Routed to review as low-value candidates (§6), kept for the monitoring tier.
- Pairs the clustering flagged that are not duplicates: `purchase-events:13` vs `:62` (one order with an exact key-set oracle vs two orders with a per-order one-to-one oracle), `virtualized-ui:69` vs `:172` (a 429 login stub vs a 500 list stub), `todo-review:25` vs `:48` (clear completed with survivors vs clearing into the empty state).

### 3.5 Dynamic subsumption

coverage-fingerprinting.md's `subsumption_candidates` applied to the request sets yields 1070 pairs and 62 candidate tests (`analysis/fingerprints.md`). It is useless as a deletion signal here and instructive as a warning: all 29 Todo tests subsume each other (one identical request), and `review-followup:33` is "subsumed" by three tests that never check its prices. Nine tests make a request nobody else makes and are load-bearing by that measure (`security:39` 403s, `baseline-shop:4` unauthenticated order calls, `baseline-shop:42/53/63` webhook 400/404/422/409/503, `baseline-shop:82` reset confirm 200, `virtualized-ui:35/172/190` the stubbed 500s and the aborted call).

## 4. Weak assertions

Scan: `analysis/weak.md` (per test: hard expects in the body and with helpers inlined, soft, poll, status-only, weak matchers, `warn` sites, `if` statements). Findings after reading the flagged tests:

- No test is assertion-free and no test is status-only. Status-only `expect(x.status()).toBe(n)` calls exist (most in `security:13` and `report-1:60`, four each) but every test also checks a body or page state.
- Checks that can never fail, by design: the 14 `probe.warn(...)` sites in `synthetic-monitoring/probes.mjs` (cacheable `/health`, missing `login` event, missing or wrong `purchase` event, budgets above the warning line). They annotate; they do not fail. The `sign-in` and `order-journey` probes' analytics checks are therefore not guards; `analytics-tracking-testing` is.
- Vacuous branch: `addons/accessibility:42` ends with a focus-visibility check whose page function returns `true` when nothing is focused (`if (!element || element === document.body) return true`). If the app dropped focus to `body` after submit, the "still visible to a keyboard user" assertion would pass. Rewrite candidate: assert that a specific control holds focus.
- Branching oracle: `virtualized-ui:142` accepts two behaviours (`Place order` disabled, or an enabled button followed by a visible `invalid_order`). Both branches assert, so it cannot pass silently, but the team should pick one. Marked `rewrite` in §6, kept as-is in `curated/`.
- Weak matchers (`toBeDefined`, `toBeNull`, `toBeTruthy`) appear only as guards before strong assertions (`performance:28`, `report-1:9`, `visual:112`).
- Self-checks of test data rather than the app: `shop-review:63` `expect(JSON.parse(raw)).toEqual(event)`, `stub-fidelity:34/59` (comparator and freshness gate). Harmless; the latter two are the detector checks AGENTS.md requires and cost 20 ms together.
- `expect.soft` is used in `stub-fidelity:11` (per-step drift, with a hard oracle over the same data) and in every probe's `finish()` (wall-clock budget). Soft expectations still fail the test at the end; they only stop short of aborting it.
